01 / 読み方

オイコム — Codexデモ実装用企画書 v1.0

作成日：2026-10-27 / 対象：日本語・スマートフォン／PC / 状態：実装前の仕様セット

サッカー開催日の、駅の混雑に備えるカレンダー。 「追い込む」と「おい！混む！」を掛けた名称。日付と駅・地域から、近くで開催される試合と来場・帰宅の注意時間帯を確認する。

このZIPは完成アプリではなく、Codexに渡す企画・画面・データ・実装指示のセットです。

使い方

  1. ZIPを展開し、フォルダー全体をCodexの作業対象にする。
  2. CODEX_START.md の本文を最初の依頼として貼る。
  3. Codexに TASKS.md のPhase 0〜5まで実装してもらう。
  4. 実装後、Codexが作るアプリのREADMEに従って起動する。

ブラウザーで読みたい場合は OIKOMU_DEMO_PLAN.html を開く。画面の見た目は design/screen_reference.html を参照。どちらも説明用資料であり、検索できるアプリではない。

この版で作るもの

  • 関東5スタジアム・7駅、2026年11〜12月の架空の試合24件。
  • 日付＋駅／地域／会場検索、月間カレンダー、駅詳細、試合詳細、お気に入り。
  • 時刻未定、延期、中止、日程変更、会場変更、会場未定の表示。
  • 日本時間で処理し、デモ基準日を2026-11-07に固定。年月が過ぎても試せる。
  • 実在の駅・会場名は場所の説明に使用。チーム・大会・対戦・開催日時・注意時間帯はすべてデモ。

02 / 企画書

01 — 企画書

1. コンセプト

名称：オイコム / 英字識別子：oikomu 副題：サッカー開催日の駅混雑カレンダー 短いコピー：その駅、今日は試合の日？

日付と場所を選ぶと、その駅の近くで行われるサッカーの試合と、来場・帰宅の注意時間帯が分かる。近隣住民の買い物・通勤・待ち合わせ、サポーターの移動計画を助ける。

名前の「追い込む」は語呂の由来として説明ページに記載する。群衆を追い込む・サポーターを迷惑扱いする表現にはしない。

2. 解決する課題と仮説

  • サッカーを見ない人は、普段利用する駅と試合日程の関係を調べるきっかけが少ない。
  • クラブの日程ページと会場のアクセスページを別々に調べる手間がある。
  • 駅を起点に試合日を一覧できれば、予定を立てるときに使える可能性がある。

需要・継続利用・予測精度は未検証。デモの目的は、駅と日付から探せるか、表示の意味を理解できるか、繰り返し利用する動機があるかの確認。

3. ユーザーと成功体験

利用者 したいこと 成功の状態
近隣住民 週末の買い物日を考える いつもの駅に関係する試合日を月表示で見つける
通勤・通学者 帰宅時間と試合の関係を見る 日付と駅を選び、帰宅の注意時間帯を読む
待ち合わせする人 その日の駅周辺を確認する 検索条件のURLを相手に渡せる
観戦者 会場へのアクセス駅を確認する 公式アクセス情報と複数の対象駅へ移れる

4. デモの範囲

関東5会場・7駅を収録する。実在施設の名称と駅の対応だけ公式案内を参考にする。以下は実際の開催日程を収録したものではない。

会場と駅の対応はSOURCES.md参照。路線全域や遠方の乗換駅へ影響を拡張しない。鉄道会社ごとの駅を別々に扱う精密な乗換モデルも作らない。

試合は架空の「サンプルリーグ」と架空8チーム、24件。基準日2026-11-07、収録期間2026-11-01〜2026-12-31。日付・対戦・開始時刻・延期等は検証用の設定であり、公式発表ではない。

5. 必須機能

ID 機能 完成の定義

実データの自動収集、プッシュ通知、地図、乗換検索、車の渋滞予測、ユーザー投稿、混雑度ランキング、観客数推計、カップ戦の延長モデル、広告・課金、アカウント、PWAのオフラインキャッシュは初版に含めない。

6. 表示上の約束

  1. 全画面上部に「デモ版｜試合・注意時間帯はサンプル。実際のお出かけ判断には使えません。」を表示。
  2. 各試合カードにも「サンプル試合」を表示し、切り抜かれても架空と分かる。
  3. 注意時間帯には「目安・デモ計算」を併記し、実測・AI予測・精度の数値を出さない。
  4. 対象試合なし、時刻未定、デモ収録範囲外、データ読み込み失敗を別々の状態として表示。
  5. 代替駅は「別のアクセス駅」と呼ぶ。空いている・確実に回避できるとは説明しない。

7. デモを見せる手順

  1. 最初は2026-11-07・全地域。3試合と5駅が表示される。
  2. 飛田給を検索し、15:00開始のm01と2つの注意時間帯を見る。
  3. 飛田給をお気に入りに登録し、再読み込みして保持を確認する。
  4. カレンダーで11月21日の「時刻未定」、22日の「延期案内」を確認する。
  5. m12の会場変更を開き、現在会場の対象駅と旧会場の案内を比べる。
  6. 2027年1月に移動し、「デモ収録範囲外」になることを確認する。

観察ポイント：駅を選べるか／開催と混雑実測を混同しないか／未定と対象試合なしを区別できるか／月表示を再利用したいか。利用分析SDKは入れず、まず対面または画面共有で確認する。

03 / 画面仕様

02 — 全画面・UI仕様

共通レイアウト

日本語・白〜薄いグレーの背景、濃紺の文字、ティールの操作色、来場はアンバー、帰宅は紫。赤や緑で混雑の強弱を演出しない。1枚のカードに日付・駅・試合・時間帯の順で配置する。

最大幅1200px、PC横余白32px、スマホ16px。本文16px以上、補助14px、タップ領域44px以上。角丸16px、枠線1px、影は薄く。表記は24時間制・日本時間。クラブロゴ、写真、外部Webフォントは使用しない。

ヘッダー：オイコム（ホーム）／探す／カレンダー／お気に入り／使い方。 その上または直下に常設デモバナー。スマホは下部ナビ「探す・カレンダー・お気に入り」、使い方はヘッダー。下部ナビに隠れない余白を本文末尾に確保。

読み込み中は短い説明とスケルトン。失敗時は「デモデータを読み込めませんでした」と再読み込み。空表示と読み込み失敗を混同しない。

S01 ホーム・検索結果

URL：#/search?date=2026-11-07&place=all&view=list

PC：タイトルと検索バー → 左280pxの場所選択／お気に入り、右に結果。 スマホ：タイトル → 日付 → 場所検索 → 選択中の場所 → 一覧／カレンダー → 結果カードの順に縦配置。

初期タイトル「その駅、今日は試合の日？」。補助「日付と駅から、サッカー開催日をチェック」。基準日ボタンは「デモ基準日へ」とする。「今日」は実日付を使わないため置かない。

検索コントロール：日付input、場所入力、候補一覧、検索ボタン。変更中の値はdraftとして持ち、検索ボタン／EnterでURLに確定。選択した場所の解除でallへ戻す。日付だけ変更して即検索しない。

場所候補は「駅」「会場」「地域」の種類を明示。最大8件。未選択の自由文が残る場合は検索を実行せず「候補から場所を選んでください」。空欄はall。候補なしは「対象の駅・地域が見つかりません」＋収録地域の案内。

結果の集約単位は駅。見出し「対象駅5駅・開催予定3試合」のように、駅数と重複を除いた試合数を分ける。各駅カードに駅名、都県、関連会場、試合、注意時間帯、星ボタン、駅詳細リンク。場所フィルターが会場ならその会場の関連駅だけ表示。

時刻がある試合を早い順、時刻未定を後ろにする。同順の駅はseedのsortOrder。延期等の案内は下の「変更のお知らせ」に分離。全地域表示では試合カードの重複が起きるが、見出しの開催件数はmatchIdでユニーク化する。

S02 月間カレンダー

URL：#/search?date=2026-11-07&month=2026-11&place=station:st-tobitakyu&view=calendar

同じ検索条件の一覧／月間切り替え。月曜始まり7列、42セル。月を切り替えたら選択日をその月1日に変更し、月と日付を一致させる。前後月セルは月付き日付を読み上げ、クリックするとその月・日を選択する。

PC：カレンダー左＋選択日詳細右。スマホ：7列の簡潔なセル＋選択日詳細を下。セルに長いチーム名を詰めず「2試合」「時刻未定」「変更」等の記号と短いラベルを表示。日セルの最低高さ52px。

表示件数は実際の会場でその日に始まるscheduled／time_tbdのユニーク試合数。前日試合の時間帯が日をまたぐ場合は別に「前日試合の帰宅目安」。延期・中止・旧会場の案内は開催件数へ加算しない。

選択日詳細：日付、開催予定、時刻未定、変更案内、注意時間帯。収録範囲内で該当なしなら「対象のサンプル試合はありません」。範囲外セルには斜線・「範囲外」を表示。色だけで意味を伝えない。

S03 駅詳細

URL：#/stations/st-tobitakyu?date=2026-11-07

駅名／読み／都県、星ボタン、日付変更、関連会場、当日の予定、次の予定5件、月表示へのリンク。 場所の公式参考リンクは「会場の公式アクセス」と表記する。デモの日程の根拠として配置しない。

次の予定は選択日を起点に昇順、scheduled／time_tbdのみ。登録期間に次の予定がない場合は「デモ収録期間内に次の予定はありません」。現在時刻を使わない。

主駅／別のアクセス駅は順位ではない。同じ会場の他駅リンクに移動できるが「おすすめ」「空いている駅」のバッジは付けない。

S04 試合詳細

URL：#/matches/m01?date=2026-11-07

サンプル試合バッジ、架空大会名、ホーム／アウェイ、開始日時、現在の会場、状態、対象駅ごとの来場・帰宅の目安。計算根拠は折りたたみ「時間帯の出し方」で見せる。

表示例（m01・飛田給）：15:00開始／来場12:30〜14:45／帰宅16:55〜18:45。必ず「デモ計算・目安」。バーの長さは時間幅であり、混雑の強さではない。

変更履歴は旧→新を日付付きで表示。延期の再日程未定、時刻未定、会場未定では不明部分を補完しない。旧会場には旧会場で開催するような時間帯を残さない。 架空の試合日程の外部URLは設けず、「この試合は架空のサンプルです」と表示。実在会場のアクセスへの外部リンクとは用途を分ける。

S05 お気に入り

URL：#/favorites?date=2026-11-07

登録した駅を登録順に表示。各駅に当日の予定と次の1件を表示。登録ゼロは「いつもの駅を登録しよう」＋場所検索へ。星ボタンは登録状態をaria-pressedで示す。

登録上限7駅（デモ全駅）。上限到達時は新規登録できないのではなく、収録駅がすべて登録済みになる。お気に入りはこの端末のブラウザーに保存される旨を補助表示。 保存不可の場合は操作自体を継続し、「この環境では保存できないため、開いている間だけ保持します」と一度案内する。

S06 使い方・対象範囲・再設定

URL：#/about

説明：何を調べられるか／デモと実測の違い／対象5会場と収録期間／日本時間／サッカー以外は対象外／名前の由来／保存するデータ。 「デモ基準日へ戻る」は検索日だけ初期化。「お気に入りをすべて解除」は確認ダイアログを出し、対象キーだけ削除。localStorage.clear()は禁止。

S07 不明なURL・読み込みエラー

未知駅・未知試合IDは「ページが見つかりません」＋検索へ戻る。存在しないIDを別の駅に置き換えない。 不正な日付パラメーターは基準日に正規化し、1回だけ「日付をデモ基準日に戻しました」。不正なplaceはallに戻す。URL全体を再読み込みし続けるループを作らない。

状態の文言

状態 主な表示
scheduled サンプル試合・開始時刻あり
time_tbd 開始時刻未定・時間帯を計算できません
venue_tbd 会場未定・対象駅をまだ表示できません
postponed 延期・新しい日程は未定です
cancelled 中止・注意時間帯は表示しません
旧会場／旧日程 変更済み・現在の開催情報を見る
対象試合なし 対象のサンプル試合はありません
収録範囲外 デモ収録範囲外です（2026年11〜12月）

アクセシビリティと操作

検索フォームはlabelを付け、候補は矢印・Enter・Escapeで操作できるcombobox/listboxとする。日付はネイティブinputでもよい。カレンダーはセマンティックな表と各日buttonで作り、無理にgridの役割を付けない。 フォーカス輪郭は2px以上。結果件数はaria-live=polite。ページ移動で見出しへフォーカス。モーダルはフォーカスを閉じ込め、閉じたら起点へ戻す。200%拡大でも操作可能にする。アニメーションは控えめでreduced-motion対応。

04 / データ設計

03 — データ設計

contracts/types.tsとdata/demo.jsonを基準にする。JSONはUTF-8、schemaVersion=1。IDは表示名と分離し、改称してもIDを変えない。

エンティティ

配列／要素 用途
meta モード、基準日、収録期間、説明
regions 東京都・神奈川県・埼玉県・千葉県
stations 7駅の名前、読み、別名、地域、並び順
stadiums 5会場の名前・別名・地域・公式参考リンク
accessLinks 会場と駅の多対多対応、デモ計算用移動分数
teams 架空8チーム。defaultStadiumIdは説明用で検索判定に使わない
matches 架空24試合。現在の会場と日付、状態、変更履歴
coverage 会場ごとの収録期間。サンプル集合内の網羅性のみを意味する
sources 実在会場と駅の対応を確認した公式出典
rules 注意時間帯のデモ計算パラメーター

1試合は現在会場0〜1、1会場は関連駅1〜複数。駅→accessLinks→会場→matchesの順に結合する。ホームチーム→本拠地の結合で試合会場を決定してはいけない。

Matchの不変条件

  • matchDateは日本時間の暦日YYYY-MM-DD。kickoffLocalTimeはHH:mmまたはnull。
  • scheduled：日付・会場・時刻が必須。
  • time_tbd：日付・会場が必須、時刻はnull。
  • venue_tbd：日付が必須、会場と時刻はnull。全地域の別枠にだけ表示。
  • postponed／cancelled：日付・会場は元の予定を保持、時刻はnull。注意時間帯を生成しない。
  • 日程変更後に確定した試合はscheduledに戻し、現在日付をmatchDateに保持。historyに旧日程を残す。同じ試合を別IDで増やさない。
  • 会場変更も現在stadiumIdを更新し、historyに旧会場を残す。
  • 同一IDは全体で一意。homeTeamIdとawayTeamIdは異なる。
  • すべての試合はisDemo=true、sourceId=null。公式アクセス出典を試合出典として流用しない。

History

fieldはmatchDate／stadiumId／kickoffLocalTime。fromValue・toValueは文字列またはnull、changedAtはオフセット付き日時、noteは「サンプル上の変更」と分かる文言。 historyは古い順。公開画面での最終変更表示は末尾、履歴一覧は新しい順でもよい。 このseedには日付と会場の同時変更は含めない。将来追加する際も逆順に履歴をたどれば変更直前のスナップショットを復元できる形にする。

時間の扱い

入力の日付と時刻から${matchDate}T${kickoffLocalTime}:00+09:00を生成する。解析・加算はタイムスタンプで、表示は必ずAsia/Tokyo。端末のタイムゾーンやtoISOString().slice(0,10)で表示日を決めない。

注意時間帯は保存せずrulesとaccessLinksから都度算出。ruleVersionを出力に付ける。サンプル移動分数は公式の徒歩時間の引用ではなくUI検証用の設定と明示する。

Coverage

5会場それぞれ2026-11-01〜2026-12-31、state=demo_complete。これはこのJSONのサンプルとしての範囲であり、実在の試合を全件掲載している意味ではない。 全地域の集計もcoverageの対象内だけで行う。範囲外では0件表示よりも「デモ収録範囲外」を優先。未知の駅名は「対象外」として候補なしにする。

保存とURL

localStorage key：oikomu:demo:v1:favorites value：{"schemaVersion":1,"stationIds":["st-tobitakyu"]} ID重複と未知IDは除去。配列でない等の破損は空に戻す。savedDateや検索履歴は保存しない。

URLではdate、month、view、placeだけを許可。place=all／station:／stadium:／region:。同時に複数種の場所を保持しない。詳細ページのdateは「戻るときの文脈」で、試合本体の日付を上書きしない。

検証ルール

読み込み時またはビルド時に、参照ID、重複、時刻形式、日付実在性、状態との整合、coverage包含を検証。致命的な参照欠損は黙って除去せずエラーにする。UIでの空状態とは分離する。 サンプルに悪意あるHTMLは含めないが、データ文字列は常にテキストとして描画。外部URLはhttps:の公式ドメインを許可し、javascript:等は拒否する。

05 / 処理ロジック

04 — 検索・カレンダー・時間帯の処理仕様

1. デモの時計

基準日=2026-11-07。初回URLに日付がなければこの日付。システムの現在日付から自動で月を移さない。sources.checkedOn=2026-10-27は参考情報を確認した実日付であり、デモ基準日とは別。

基準日は検索の入口であり、「その日現在に判明していた情報」を再現する時点検索ではない。変更履歴はデモ集合の最新状態を表示する。変更時刻が基準日より後でも履歴を巻き戻さない。

2. 検索の順序

  1. URLとフォーム入力を検証する。
  2. 選択場所を駅集合／会場集合に展開。regionは会場のregionIdで絞り、その会場の関連駅を表示。
  3. 選択日がcoverageに含まれるかを判定。
  4. 現在会場に一致するscheduled／time_tbdのうち、matchDateが選択日、または算出時間帯が選択日に重なる試合を抽出。
  5. 旧日付・旧会場の変更案内、延期・中止を別枠に抽出。全地域に限りvenue_tbdも別枠に表示。
  6. 駅ごとにカード化。開催試合数は現在日付が選択日のscheduled／time_tbdをmatchIdで重複排除して数える。

全地域で同じ試合が2駅に出ても開催件数は1。会場未定は開催件数へ含めず「会場未定1件」と別表示。変更案内だけの駅も表示するが、「時間帯を計算した駅数」へは含めない。 候補の正規化はNFKC、前後空白除去、英字小文字、カタカナ→ひらがな。name・kana・aliasesから部分一致。数字は維持。あいまいな駅の自動確定はしない。

3. 注意時間帯の算出

以下は実測・公式推奨ではなく、デモ表示のための仮定。全会場共通rulesから初め、将来の本番では検証する。

K=開始時刻、W=accessLinks.demoWalkMinutes。

パラメーター 初期値 意味
arrivalStartBeforeMinutes 150 来場の注意時間帯が始まる開始前分数
arrivalEndBeforeMinutes 15 来場の注意時間帯が終わる開始前分数
matchEndEarliestAfterMinutes 110 最短の終了見込み（開始から）
matchEndLatestAfterMinutes 130 最長の終了見込み（開始から）
departureTailMinutes 90 終了後の流れを見るための仮の幅

来場：[K−150分, K−15分) 帰宅：[K＋110分＋W, K＋130分＋W＋90分)

来場帯にはWを加減しない。この初版の来場帯は駅ごとの違いを推計せず、開始前の共通目安として扱う。帰宅帯だけ移動分を加える。退場時のゲート待機や列車待ちは分離推計しないため、「改札待ち時間」「乗車までの時間」と言い換えない。

例：m01、2026-11-07 15:00、飛田給W=5 → 来場12:30〜14:45、帰宅16:55〜18:45。 同じm01、多磨W=20 → 帰宅17:10〜19:00。差はデモ移動分数によるもので、混雑量の差ではない。

scheduledかつ会場・時刻・対応駅が揃う場合だけ計算。time_tbd／venue_tbd／postponed／cancelledは空配列を返し、理由コードをUIへ渡す。 開催終了時刻が公式に得られた場合の上書き、延長・PK、試合後イベント、天候、臨時列車は初版で推計しない。

4. 日またぎ・区間の境界

区間は開始を含み終了を含まない半開区間[start,end)。表示上はHH:mm〜HH:mmでよい。 日付Dの区間は[D 00:00+09:00, 翌日00:00+09:00)。重なりはmax(start,dayStart)<min(end,dayEnd)。0分の区間は非表示。 日付ごとの表示はクリップするが、試合詳細には「翌日」等のラベル付きで元の日時を示す。日付が変わる場合は日付も明記。終端24:00の表示は日表示に限り許容する。

5. 複数試合の時間帯

駅・日付・種別（来場／帰宅）ごとに並べ、重なる区間または端点が一致する区間を結合。結合後もmatchIdsの集合を保持。種別の異なる区間は結合せず2段にする。 結合しても混雑段階や色の濃さを増やさない。「複数のサンプル試合による目安」と説明する。 タイムラインは06:00〜24:00を基本とするが、それより前に区間がある日は00:00から表示。ラベルはその日の実際の区間に合わせる。

6. 状態変更

  • m09：時刻未定。11/21の開催1件、時間帯なし。
  • m10：11/22の延期。浦和美園に変更案内だけ表示、開催0件、時間帯なし。
  • m11：11/23の中止。蘇我に変更案内だけ表示、開催0件、時間帯なし。
  • m12：11/28の会場が味の素→日産に変更。小机・新横浜には開催と時間帯、飛田給・多磨には旧会場の変更案内のみ。
  • m13：開催日が12/05→12/06へ変更。12/05は柏に変更案内のみ、12/06に開催と時間帯。
  • m24：12/20の会場未定。全地域の別枠だけ。ホームチームの本拠地で駅を推測しない。

historyから旧開催情報を作る時は、現在のスナップショットから逆順に変更を戻して各変更直前の状態を得る。旧スナップショットに紐づく日付・会場・駅で案内する。現在試合と案内は同じmatchIdへのリンクを持つ。

7. URL・画面遷移

正規URLの例：#/search?date=2026-11-07&place=station%3Ast-tobitakyu&view=list。 URLSearchParamsで生成し、文字列の無加工連結を避ける。検索確定・日付クリック・月送りは履歴に追加、パラメーター正規化はreplace。 一覧／月間はplace・dateを保持。ブラウザーの戻る／進む、直接アクセス、再読み込みで同じ結果になる。monthがdateと異なる場合はdateの月を優先してmonthを直す。 共有はURLコピーを必須とし、Clipboard APIが使えなければ選択できるテキスト欄を開く。任意の端末共有は機能検出後のみ。localhostのURLは他端末から開けないことを補足し、架空の公開URLを発行しない。

8. 出力型と責務

calculateWindows(match, accessLink, rules)は日時区間・kind・matchIds・ruleVersionを返す純粋関数。 filterMatches、buildChangeNotices、clipToDay、mergeWindows、summarizeDay、normalizeQueryをUIから独立させる。 計算ができないときの理由コードをtime_tbd等の状態文言へマッピングする。数値0を「未定」の代わりに使わない。

06 / 技術仕様

採用方針

新規ならReact＋TypeScript＋Viteの静的SPA。サーバー、DB、秘密鍵、アカウントは不要。開発環境がオフラインなら既存依存を確認し、導入できないものを実行済みと扱わない。 Viteは公式にreact-tsテンプレートを提供する。Nodeの条件と依存互換性は実装時の公式ガイド・package enginesで確認し、実際に使用したバージョンをREADMEに記載する（SOURCES.md参照）。

データ層

デモJSONはアプリに同梱し、ネットワーク取得しない。データ層のgetDataset()から取得し、後に実データへ切り替える余地を作る。demoとliveのレコードを混在させない。 公開するのはビルドした静的ファイル。設定にサーバー用キーを含めない。外部サイトはリンクを押したときだけ開く。外部スクリプト・広告・アクセス解析・CDNの字体を入れない。

UI状態

セキュリティ・堅牢性

文字列はReactの通常テキスト描画。dangerouslySetInnerHTMLを使用しない。URLパラメーターの許可リスト、外部リンクのhttps制限、target=_blank時のnoopener noreferrerを実装。 localStorage.getItem/setItem/JSON.parseを例外処理する。削除は該当キーのみ。お気に入り以外の閲覧情報を送信しない。 デモデータで実在のクラブロゴや写真、公式の試合表のコピーを使わない。アプリ内に実在クラブが架空日程で試合するような表示をしない。

開発と確認

実装後はnpm install、npm run dev、npm run build、npm run previewを使えるようにする。test、typecheckを追加。ローカル起動のポートは実行結果のURLを案内。 unit：日時境界、未定等の抑制、件数重複、変更履歴、URL、保存データ破損。 browser：主要検索→詳細→お気に入り→再読み込み、キーボード操作、360／390／768／1440px、横スクロール、console error。 アプリを作っていない段階でbuild成功と報告しない。公開前の作業は別途依頼があった時だけ行う。

07 / 実データ化

06 — 実データ運営への移行メモ（デモ実装対象外）

デモで確認すること

日付と駅の2条件で迷わないか、月表示が生活予定に使えるか、目安と実測を区別できるかを確認する。収益や継続率は現時点では見積もらない。

実データ版に必要な追加作業

  1. 対象リーグ・大会・会場を確定し、公式情報を確認する担当と更新頻度を決める。
  2. 提供条件に応じたデータ取得方法を用意する。自由に使える公式APIがある前提で進めない。初めは手動登録・確認でもよい。
  3. 発表時期、日程未定、開始時刻未定、会場未定、延期、中止、変更履歴を管理する。
  4. 試合ごとに公式出典URLと最終確認日時、データセット全体の更新状態を付ける。アクセス資料の確認日時で試合の鮮度を代替しない。
  5. 取得失敗・未確認・一部収録を区別する。更新が止まった時に「試合なし」と表示しない。
  6. 会場名称変更やアクセス駅・歩行経路の変更を定期確認する。
  7. 実測や公式の案内に基づき注意時間帯の仮定を評価する。デモ係数を検証済み予報として公開しない。
  8. デモ専用データを本番から除外し、別モード・別URLでのみ提供する。

将来の機能候補

お気に入り駅のカレンダー購読、対象会場追加、公式の臨時列車・交通案内へのリンク、店舗向けの埋め込みカレンダー。実装順は利用確認後に決める。 広告や地域協賛は情報の正確性と日常利用を確かめてから検討。掲載料によって注意表示や駅の並び順を変えない。

対象外の線引き

サッカー以外のコンサート等、通常の通勤ラッシュ、運休、駅入場規制のリアルタイム把握、バス・車の混雑までは扱わない。サッカーの試合がないことは駅が空いている根拠にはならない。
