# 04 — 検索・カレンダー・時間帯の処理仕様

## 1. デモの時計

基準日=2026-11-07。初回URLに日付がなければこの日付。システムの現在日付から自動で月を移さない。sources.checkedOn=2026-10-27は参考情報を確認した実日付であり、デモ基準日とは別。

基準日は検索の入口であり、「その日現在に判明していた情報」を再現する時点検索ではない。変更履歴はデモ集合の最新状態を表示する。変更時刻が基準日より後でも履歴を巻き戻さない。

## 2. 検索の順序

1. URLとフォーム入力を検証する。
2. 選択場所を駅集合／会場集合に展開。regionは会場のregionIdで絞り、その会場の関連駅を表示。
3. 選択日がcoverageに含まれるかを判定。
4. 現在会場に一致するscheduled／time_tbdのうち、matchDateが選択日、または算出時間帯が選択日に重なる試合を抽出。
5. 旧日付・旧会場の変更案内、延期・中止を別枠に抽出。全地域に限りvenue_tbdも別枠に表示。
6. 駅ごとにカード化。開催試合数は現在日付が選択日のscheduled／time_tbdをmatchIdで重複排除して数える。

全地域で同じ試合が2駅に出ても開催件数は1。会場未定は開催件数へ含めず「会場未定1件」と別表示。変更案内だけの駅も表示するが、「時間帯を計算した駅数」へは含めない。
候補の正規化はNFKC、前後空白除去、英字小文字、カタカナ→ひらがな。name・kana・aliasesから部分一致。数字は維持。あいまいな駅の自動確定はしない。

## 3. 注意時間帯の算出

以下は実測・公式推奨ではなく、デモ表示のための仮定。全会場共通rulesから初め、将来の本番では検証する。

K=開始時刻、W=accessLinks.demoWalkMinutes。

|パラメーター|初期値|意味|
|---|---|---|
|arrivalStartBeforeMinutes|150|来場の注意時間帯が始まる開始前分数|
|arrivalEndBeforeMinutes|15|来場の注意時間帯が終わる開始前分数|
|matchEndEarliestAfterMinutes|110|最短の終了見込み（開始から）|
|matchEndLatestAfterMinutes|130|最長の終了見込み（開始から）|
|departureTailMinutes|90|終了後の流れを見るための仮の幅|

来場：[K−150分, K−15分)
帰宅：[K＋110分＋W, K＋130分＋W＋90分)

来場帯にはWを加減しない。この初版の来場帯は駅ごとの違いを推計せず、開始前の共通目安として扱う。帰宅帯だけ移動分を加える。退場時のゲート待機や列車待ちは分離推計しないため、「改札待ち時間」「乗車までの時間」と言い換えない。

例：m01、2026-11-07 15:00、飛田給W=5 → 来場12:30〜14:45、帰宅16:55〜18:45。
同じm01、多磨W=20 → 帰宅17:10〜19:00。差はデモ移動分数によるもので、混雑量の差ではない。

scheduledかつ会場・時刻・対応駅が揃う場合だけ計算。time_tbd／venue_tbd／postponed／cancelledは空配列を返し、理由コードをUIへ渡す。
開催終了時刻が公式に得られた場合の上書き、延長・PK、試合後イベント、天候、臨時列車は初版で推計しない。

## 4. 日またぎ・区間の境界

区間は開始を含み終了を含まない半開区間[start,end)。表示上はHH:mm〜HH:mmでよい。
日付Dの区間は[D 00:00+09:00, 翌日00:00+09:00)。重なりはmax(start,dayStart)<min(end,dayEnd)。0分の区間は非表示。
日付ごとの表示はクリップするが、試合詳細には「翌日」等のラベル付きで元の日時を示す。日付が変わる場合は日付も明記。終端24:00の表示は日表示に限り許容する。

## 5. 複数試合の時間帯

駅・日付・種別（来場／帰宅）ごとに並べ、重なる区間または端点が一致する区間を結合。結合後もmatchIdsの集合を保持。種別の異なる区間は結合せず2段にする。
結合しても混雑段階や色の濃さを増やさない。「複数のサンプル試合による目安」と説明する。
タイムラインは06:00〜24:00を基本とするが、それより前に区間がある日は00:00から表示。ラベルはその日の実際の区間に合わせる。

## 6. 状態変更

- m09：時刻未定。11/21の開催1件、時間帯なし。
- m10：11/22の延期。浦和美園に変更案内だけ表示、開催0件、時間帯なし。
- m11：11/23の中止。蘇我に変更案内だけ表示、開催0件、時間帯なし。
- m12：11/28の会場が味の素→日産に変更。小机・新横浜には開催と時間帯、飛田給・多磨には旧会場の変更案内のみ。
- m13：開催日が12/05→12/06へ変更。12/05は柏に変更案内のみ、12/06に開催と時間帯。
- m24：12/20の会場未定。全地域の別枠だけ。ホームチームの本拠地で駅を推測しない。

historyから旧開催情報を作る時は、現在のスナップショットから逆順に変更を戻して各変更直前の状態を得る。旧スナップショットに紐づく日付・会場・駅で案内する。現在試合と案内は同じmatchIdへのリンクを持つ。

## 7. URL・画面遷移

正規URLの例：`#/search?date=2026-11-07&place=station%3Ast-tobitakyu&view=list`。
URLSearchParamsで生成し、文字列の無加工連結を避ける。検索確定・日付クリック・月送りは履歴に追加、パラメーター正規化はreplace。
一覧／月間はplace・dateを保持。ブラウザーの戻る／進む、直接アクセス、再読み込みで同じ結果になる。monthがdateと異なる場合はdateの月を優先してmonthを直す。
共有はURLコピーを必須とし、Clipboard APIが使えなければ選択できるテキスト欄を開く。任意の端末共有は機能検出後のみ。localhostのURLは他端末から開けないことを補足し、架空の公開URLを発行しない。

## 8. 出力型と責務

calculateWindows(match, accessLink, rules)は日時区間・kind・matchIds・ruleVersionを返す純粋関数。
filterMatches、buildChangeNotices、clipToDay、mergeWindows、summarizeDay、normalizeQueryをUIから独立させる。
計算ができないときの理由コードを`time_tbd`等の状態文言へマッピングする。数値0を「未定」の代わりに使わない。
